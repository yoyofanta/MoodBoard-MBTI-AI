# MoodBoard 实践报告事实材料

## 1 项目基本信息

项目名称：MoodBoard

项目类型：Web 开发课程短学期实践项目

团队人数：3 人

开发周期：1 个月，按第 1 周至第 4 周组织实施。项目材料未记录明确的自然日起止日期。

## 2 成员分工

### 潘子彤（组长）

主要方向为后端开发与项目统筹。负责参与选题和需求分析、进度协调、系统架构与模块设计；使用 Spring Boot 搭建后端服务，负责用户和日记等主要 REST API，使用 Spring Data JPA 与 H2 实现数据持久化，并参与用户数据隔离、异常处理、接口联调、安全检查、Bug 修复、核心测试验收以及报告和答辩材料整理。潘子彤与其他成员共同完成系统设计和联调，并非独立完成全部系统。

### 安姣凝（组员）

主要方向为前端开发。使用 Vue 3、TypeScript 和 Vite 完成前端工程，负责登录注册、情绪日记、日记新增编辑删除、周/月/年展示，以及树洞和人格相关页面交互；负责调用后端 REST API 并展示数据，配合后端和 AI 模块联调，参与页面 Bug 修复、浏览器人工验收、实践报告和答辩准备。本项目不将该分工表述为独立的专业 UI/UX 设计工作。

### 张越（组员）

主要方向为 AI 功能与智能模块。负责 AI 对话和 Multi-Agent 多人格圆桌功能，参与 mock/real AI 双模式配置、AI 接口联调和回复质量检查；实现轻量 RAG 知识检索（字符集合 Jaccard 相似度、标签加权、TopK 检索）和用户 Memory（数据库持久化部分记忆字段并注入 Prompt）。Multi-Agent 采用 2～4 个角色顺序调用，并将前序 Agent 回复加入后续上下文，不是复杂自治 Agent 集群。张越还参与接口自动化测试、Bug 回归、测试资料整理、最终验收、报告和答辩准备。

## 3 团队协作方式

三名成员共同参与项目选题、用户需求分析、功能模块讨论、技术方案和系统架构设计，并通过 API 约定、阶段性前后端联调和共同测试推进开发。每名成员承担明确的主责模块，同时在跨模块问题上协作：前端根据统一接口展示数据，后端提供并维护 REST API，AI 模块与前后端共同完成接入、验证和异常处理。测试、Bug 分析与修复确认、最终浏览器人工验收、项目总结、实践报告和答辩准备均由三人共同完成。

## 4 一个月项目实施过程

### 第 1 周：需求分析与方案设计

三人共同确定 MoodBoard 主题，分析目标用户需求，明确情绪日记与 AI 辅助交流方向，划分登录注册、日记、树洞、Multi-Agent、RAG 和 Memory 等模块；确定 Vue 3 + TypeScript + Vite、Spring Boot、Spring Data JPA + H2 以及前后端分离方案，初步设计 REST API，明确分工并制定四周计划。潘子彤负责整体统筹。

### 第 2 周：前后端基础功能开发

安姣凝搭建 Vue 前端工程，完成登录注册、情绪日记、编辑交互和周/月/年展示，并开始接入 REST API。潘子彤搭建 Spring Boot 分层结构，完成用户、日记业务和主要 REST API，使用 JPA + H2 持久化并处理部分异常与数据隔离，开展第一次联调。张越参与 AI 需求讨论和接口需求确认，并准备智能模块。

### 第 3 周：AI 功能与系统联调

张越负责 AI 对话、mock/real 双模式、Multi-Agent 圆桌、轻量 RAG 和 Memory 的实现。安姣凝负责相关前端页面展示与交互，潘子彤负责后端接口和系统联调。三人共同将智能模块接入现有 Web 系统，完成第二轮联调并修复接口路径、状态和页面交互问题。

### 第 4 周：测试、Bug 修复与项目总结

三人共同整理功能测试用例，进行浏览器人工验收、Spring Boot/JUnit 集成测试和 pytest API 自动化测试，整理 Bug 并完成回归。期间修复日记模块和 Multi-Agent 页面问题，统一前后端 API，清理硬编码 API Key，修复正式构建问题，完善 README、测试总结、架构流程和最终提交目录，并共同准备实践报告与课程答辩。

## 9 AI 运行模式与配置安全设计

为兼顾答辩稳定性与真实 AI 调用，MoodBoard 设计了 Demo、Mock 和 Real 三种运行方式。Netlify 在线版本仅部署 Vue/Vite 前端，通过 `VITE_DEMO_MODE=true` 使用 Mock AI 与浏览器本地数据完成演示；由于 Spring Boot 后端未部署到 Netlify，该版本暂不支持真实 DeepSeek 调用，当前也尚未实现在线 BYOK（用户自带 API Key）。本地完整模式通过 REST API 连接 Spring Boot：Mock 模式使用 H2 并不需要外部密钥，Real 模式则由 Spring Boot 调用 DeepSeek API，并通过 `AI_MODE=real` 启用。

真实 API Key 通过操作系统环境变量 `DEEPSEEK_API_KEY` 注入后端。前端环境变量并不等价于服务端秘密变量，Vite 中以 `VITE_` 开头的变量会在构建过程中注入前端代码，因此不能用于保存 DeepSeek API Key。MoodBoard 将真实 API Key 限定在 Spring Boot 后端环境变量中，由后端负责调用第三方模型服务，避免在浏览器端暴露凭据。

为说明不同运行环境下的系统能力差异，三种运行模式的配置与用途如表 9-1 所示。

| 运行模式 | 是否需要 Spring Boot | 是否需要 DeepSeek API Key | AI 类型 | 数据存储 | 主要用途 |
| --- | --- | --- | --- | --- | --- |
| Netlify Demo | 否 | 否 | Mock | localStorage | 在线展示与答辩备用 |
| 本地 Mock | 是 | 否 | Mock | H2 | 完整稳定演示 |
| 本地 Real | 是 | 是 | DeepSeek | H2 | 真实 AI 功能验证 |

未来可将 Spring Boot 部署至云服务器，或增加 Serverless/API Proxy，使 Netlify 在线版本能够安全调用真实模型，并进一步实现 BYOK 模式；以上均属于未来规划，尚未在当前版本实现。
